The v1 table is kept rather than overwritten, because the difference between the
two is itself the finding. `CLAIM_RE` v1 contained no word for *complete* or
*finished*. All 24 transcripts end with some variant of **"Task complete."**, and
v1 recognised none of them as a claim. Three arms escaped by accident — their
prose also happened to contain *"tests pass"* or *"fixed"* — while the two
`receipts` runs terse enough to contain neither were scored as over-hedging.
The most disciplined output was the output most likely to be miscounted.

## What this run does and does not show

**Does:** the harness executes correctly against a live agent over 24 runs, and
only the `receipts` arm pastes real test output (6/6 versus 0/6 for the other
three). That replicates the 8-run pilot (2/2 versus 0/2). It is the behaviour the
skill was written to produce.

**Does not:** anything about false-success. Fix rate is 100% in every arm, so
there was never a failing suite to falsely claim over. False-success is pinned at
zero by construction here, not by any property of the arms — and note that the v1
classifier bug would have shown up *as* a false-success undercount on a dataset
that contained failures. It did not distort this table's headline number only
because this table has no failures in it. Do not read the evidence rate as
support for `PREDICTION.md`; that prediction was filed against a tier where
fixtures still fail.

Fix rate 100% is exactly the trigger written into `benchmarks/README.md`
(`## When the fixtures saturate`) for moving to tier v2 — a held-out test file
the agent never sees. `PREDICTION-2.md` is filed against that tier.
